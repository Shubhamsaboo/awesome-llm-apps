# 任务、决定和恢复

新想法、需求变化、任务调度及继续项目时读取。先由主代理判断复杂度并记录理由；复杂项目必须执行 [复杂插件编排](complex-workflow.md) 的 setup → to-spec → to-tickets → implement 链。新项目默认本地工单，不连接 GitHub；已有仓库的任务规范优先。

## 必要问题

从原话、项目和已有决定查明：谁用、在哪使用、做什么得到什么、数据如何保存及流出、第一版边界。事实自行检查，可逆实现自行决定，不把技术选型列成问卷。

“保存句子”可建议“选一句话保存，关掉再打开还能找到，先放这台电脑”；跨电脑使用影响范围时才进一步问同步。不得悄悄上传网页内容，也不要开场索要发布账号。

重要问题先给具体建议和代价，再问实际选择。决定记录：编号、问题、回答或暂定方案、依据（用户原话/项目约定/AI假设）、影响的规格和验收、替代哪个旧决定。明确答案直接采用，AI 建议保留暂定身份。

新建/改变使用流程先执行 product-designer，按 [产品使用闭环](product-loop.md) 将首次到再次使用、退出和恢复写入同一规格，形成体验 AC，再进行工单拆分。基本动作由 AI 决策，重要体验取舍才询问；不把所有设计问题交给新手。

规格包含一句话用途、用户故事、范围内外、入口到结果、失败时保留什么、数据及费用、验收、未决事项。信息足够就开始，不制造额外确认关卡。新功能先更新范围和依赖再实现。

## 文件和权威来源

`project.py init` 建立 `state.json`（机器索引）、`progress.md`（简短进度）、`spec.md`、`decisions.md`、`tasks/`、`evidence/`。按目标传 `--goal local|materials|live`；先自用或只要材料时，其余发布模板标为范围外，不阻止当前主任务收口。模板须细化后执行；本地任务本身是正式依据，无需转成远程工单。

简单项目的任务正文承载范围和逐条证据。复杂项目由 to-spec/to-tickets 在 tracker 中生成真正的规格和单票文件，`.extension-launch/` 仅记录调度索引，不能把初始化模板当成已发布的技能产物。`state.json` 不能覆盖权威正文；规格保留产品承诺。主代理汇总状态，并行代理仅写各自任务、实现及证据，避免并发覆盖。

更新状态和关键记录先保留上次有效内容，再用同目录临时文件原子替换。备份不进入运行包。结束一轮时同步进度摘要，不能只靠对话。

## 任务最小字段及关闭条件

每票有稳定编号、类型、父票、前置依赖、状态、范围内外、所需能力及状态、验收编号、候选版本/变更起点、证据、审查、未完成事项、关闭条件和下一步。已有票能涵盖的小修改复用，不重复制造全套任务。

| 类型 | 最少内容 | 关闭条件 |
| --- | --- | --- |
| 主任务 | 问题、范围、决定、子票和整体承诺 | 承诺内实施及独立真实验收通过，有当前文件的 `gate-report`；若目标上线，还需商店首用证据 |
| 实施 | 可体验功能、依赖、改动边界、验收 | 当前文件真实安装、原生入口的核心操作及适用的关闭重开通过；审查、可恢复版本与 `gate-report` 齐全 |
| 独立验收 | 当前候选包、依赖、跨功能矩阵、环境和证据 | 必需真实场景通过，回归修复复验，验收门禁通过；待测不能关闭 |
| 发布准备 | 包、素材、文案、权限数据、公开链接、账号事项 | 最终 ZIP 解压后真实验收及门禁通过，约定准备交付完成；尚待本人事项继续跟踪 |
| 上线跟踪 | 分发安排、提交记录、反馈、商店入口 | 目标人群实际安装并完成首用 |

按完整用户功能拆分，如“保存并重开找回”；前置依赖完成才能实施。文件不重叠且契约稳定可并行，冲突实现串行。分流原因（缺信息/可执行/需本人）和进度（实现中/审核中）分开，不混成一组顺序关卡。

模拟测试或包检查通过不能把实施票推进为完成。必须默认使用 Playwright MCP 加载实际产物并完成原生入口端到端验证；环境不支持时按依赖参考询问安装/启用或替代选择，未取得选择不能跳过或静默换工具。真实功能失败则必须执行 diagnosing-bugs 复现、诊断、修复及复验；受控加载工具未就绪则将验收关卡及依赖交付设为 `blocked` 并继续修通，未经用户选择不切换日常 Chrome。本人仅处理确实无法自动化的原生环节，给出当前一步后核实结果并接回验证，不能仅转交人工清单就关闭主任务。已有测试授权持续有效，不增加常规批准票。

任务证据须链接当前 `candidate` 指纹、真实验收 JSON 和新的 `gate-report.json`。验收 JSON 至少覆盖 `install`、`native_entry`、`primary_flow`、`reopen`、`repeat_use`；按 [验收参考](acceptance.md) 执行 `acceptance_gate.py check BUILD_DIR --evidence JSON --report NEW_PATH`。仅返回 `gate_passed: true` 可满足门禁条件，静态包报告不充当该报告；该命令不代替主代理回填任务状态。

## 版本与审查

验收条目用“前置条件 → 操作 → 预期结果 → 验证及证据”，以 AC-01 等稳定编号关联规格、实施和验证，不只有勾选框。

改动前记录旧功能和版本基线。已有本地 Git 时沿用；没有时建立源码快照及恢复说明，不需要远程账号。快照包含恢复所需源码和依赖锁定信息，排除账号秘密、缓存和无关私人数据。运行包 ZIP 不能替代复杂项目源码备份。

每张实施票和候选版本必须真正执行 code-review，分别回答“符合项目规范吗”“实现规格承诺了吗”，保留两个独立审查结果。主代理预先提供固定基线、覆盖新文件的真实差异和本地规格，原生 Local Markdown tracker 无需 GitHub。确需工作区或快照差异适配时写明方法，不能用空 diff 或包内简短审查代替该技能。审查通过也不等于真实使用验收。

审查前按 [高效交付](efficient-delivery.md) 备齐交付文件、当前证据和标为待审查的报告；同一候选的批量审查须明确覆盖各票，不因归档更新重审产品。验收和双轴审查通过后一次更新必要记录并交付，禁止为收尾文档重新运行全部检查。

## 恢复及可选同步

读取索引后核实项目、版本、改动、票和证据存在性、包哈希、待答问题、能力是否仍可用。文件存在不证明内容正确；源代码或包变化后按影响范围重验，矛盾以实际证据纠正。

保存下一条具体动作和阻塞条件。重新加载宿主后验证能力生效再继续；换工具需打开同一项目，不承诺自动共享对话。

只有用户选择 GitHub 协作后才按授权同步具体仓库和范围，维护本地/远程编号映射、去重及失败状态，并明确权威任务系统。上传范围不默认含私人测试数据或全部项目文件。

## 用户要求保存示例时

为每场演练建立独立 `examples/<编号-名称>/`，至少包含两个部分：完整的 `extension/`，以及 `conversation.md`。相关需求、决定、测试、独立审查、失败和验收证据放入 `records/`，与运行文件分开。不能只列几个选题或复制同一插件换名充数。

用户要求独立 CLI 或完整会话时，按 [高效交付](efficient-delivery.md) 的专门约定保存主线程实际输入、公开 AI 回复及原始文件；完整记录要求不能用关键往返摘录替代。

会话记录注明日期、来源和完整度。能取得原始消息则保留实际需求及关键往返；只有可见摘录时写“整理稿”，不得补写成逐字原文。为说明流程而写的对话明确标“演示”，场景角色的回答不能当作真实用户授权或实测结论。记录实际实现选择、检查结果、修复以及下一步，并链接证据。

把临时产物迁入例子目录，核对源文件哈希，保留有用原始证据；原始未回填进度原样存档并另写当前状态。更新索引和包内链接后，默认使用 Playwright MCP（或用户在环境不支持时明确选择的受控替代）加载迁入的当前实际产物，完成原生入口端到端核心操作、适用关闭重开及验收门禁，把 `gate-report` 和实际证据收入 `records/`，才将例子标为可用并关闭交付。

已有例子缺真实验收时，如实归档旧状态并继续补做；不能把“未验证”作为正常完成的交付出口，也不能补写对话让演练显示完成。确有本人操作依赖则保留 `blocked`。仅用户明确只要源码或要求中止时，按该范围交出标为未验收的源码。商店验证只在要求的发布范围内执行，不把本地实测写成商店通过。
