# 产品使用闭环

新建插件、改变用户流程或处理体验缺陷时，必须实际执行 `product-designer`。输入用户原话和已有决定，输出写入现有规格，不另建一套产品文档。小需求用短段落或表格即可；只读技能名字、列功能清单不算完成。

## 从开始到下一次使用

规格在拆票前必须回答：用户从哪里进入、做什么、如何知道成功、如何处理结果、如何继续下一次、如何结束，以及取消/失败后如何恢复。逐状态写出可见反馈、可发现的下一动作与数据保留方式，并形成体验 AC。

结果页不能只有结果而无后续动作。例如取色应从结果面板“重新取色”进入下一轮，保留已选结果并支持取消返回；不能默认要求用户关面板再去浏览器工具栏重启。按钮、快捷键和连续模式只是实现选项，选符合任务的最短可发现路径，不强制所有插件套相同界面。

自动型插件没有结果面板时，闭环是后续网页/事件继续自动生效，并且用户可发现状态、暂停、恢复和退出方式；不要为去广告或自动跳转硬加每次确认。确属一次性操作则第二轮用下一项输入或再次访问验证，不能把“没有再次按钮”直接判失败，也不能用“不适用”豁免整个闭环检查。

## AI 决策与用户决策

- AI 主动补齐再次操作、取消、关闭、成功反馈、错误恢复等基本路径，记录为设计决定，不要求用户逐按钮批准。
- 连续采集还是单次确认、自动执行还是先预览、覆盖还是追加等明显影响用途/数据或打断程度的选择，先从上下文判断；信息不足时向用户用日常场景说明推荐和取舍，等待必要答案，再实施依赖部分。技术拆分、框架、测试方法仍由 AI 决定。
- 不把“用户没提”当作缺少基本闭环的理由，也不以补闭环扩成账号、云同步、批量管理等无关功能。

## 真实连续使用验收

最终候选必须增加 `repeat_use` 必需场景：从已验证的真实入口开始，连续完成两轮任务，第二轮通过用户可发现的正常路径继续；记录每轮入口/触发、实际结果，以及第二轮如何开始。再实际验证结束、取消或失败后的可恢复状态。

交互型插件优先使用真实 MCP 点击、键盘或指针操作。不得通过脚本调用内部处理器、强设存储、隐藏快捷方式或重新初始化页面来替代用户继续操作；读取 DOM/存储和确定性测试数据可作核对。浏览器原生入口本来就必须使用时，记录平台约束及为什么该路径合理，不机械禁止工具栏操作。

例如取色连续选 A、复制、在面板再次取 B、取消或退出；自动跳转连续访问两个受支持外链；广告过滤在动态插入或下一网页继续工作，并实际暂停/恢复。以上仅为场景设计参考，不自动触发修改或重测已有例子。

code-review 的 Spec 轴须核对这条闭环本身是否完整，不能只看已有 AC 全打勾。`product-designer` 对实际页面的反馈、继续操作和恢复结果做体验复核，复用同一批浏览器证据，不新开整套流水线。若规格遗漏必要基本动作，先补体验 AC，再修复，不以实现“符合不完整规格”关闭问题。

最终报告分列“技术功能”与“使用闭环”，分别说明通过/未通过及证据。缺再次操作或只能靠绕路完成任务时，技术测试通过也不能称完整可用。验收门禁只验证证据结构与版本，不能自动判断入口是否易发现；需保留实际界面、连续操作与上述复核结论。

## 证据字段与旧记录

`repeat_use` 沿用场景的 steps、expected、actual、artifactPaths；另含 `rounds` 数组，至少两项，每项填写实际非空 `entry`（用户入口/自动触发）和 `outcome`；`continuation` 描述两轮如何衔接，`exit_or_recovery` 描述实际退出或恢复结果。不得预填通过或用字段齐全冒充操作发生。

新门禁要求此场景；旧报告缺失时将不能通过新检查。保留旧报告和历史结论，不自动重写、补造证据或启动用户已停止的例子。继续该项目时再补齐实际验收，并标明原有技术检查与新体验检查的区别。
