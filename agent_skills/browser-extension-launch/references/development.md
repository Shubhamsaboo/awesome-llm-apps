# 制作第一版、审查与排错

实现或修复时读取。先读规格、前置票、既有规范和待保护的旧功能；了解代码时遵从项目索引约定。首条路径完成实现后，必须在真实 Chrome 安装并从原生入口验收通过，才能交付为可用扩展。

## 先执行必需技能，再选择起点

每次进入扩展开发先读取并执行 chrome-extensions 的相关规则和引用资源。新项目必须执行 extension-create：主代理把已知名称、用途、功能、框架选择作为明确输入，实际运行所选脚手架、配置入口和最小权限，再构建核实；不能只读一次说明就复制包内模板而称初始化完成。

技术选择由 AI 在用户授权内完成，不再问新手 React/Vue/WXT 等。extension-create 当前支持 WXT/CRXJS；按真实版本和官方文档准备 Node、包管理器及命令，简单功能也可选轻量模板。已有项目保留既有结构和锁文件，不为了满足初始化节点再重建，记录该节点因接手已有项目不适用。

复杂度由主代理自行识别，命中条件必须走 [复杂插件编排](complex-workflow.md)，每张实施票显式调用 implement；该技能要求 tdd 时按行为边界执行。原生参考模板和 examples 只作为代码阅读素材，不替代必需调用。用户已停止的例子不因更新编排而继续运行。

实现前按 [高效交付](efficient-delivery.md) 提取当前必需技能的硬规范并尽早检查；涉及共享设置时，先验证并发读写和异常后继续操作。特殊浏览器能力尽早探测，不在最终验收才发现环境不支持。

## Chrome 实现要点

- 每项权限对应功能。点击后临时读当前网页可评估 activeTab 与 scripting；持久网站访问才选窄化 host permissions，并处理临时授权生命周期。不要默认所有网站、tabs、debugger 等权限。[activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)
- popup 会关闭，service worker 会休眠；需要保留的内容写入适合存储，不靠后台全局变量永存。读写失败反馈给用户，迁移不能每次启动清空旧内容。[后台生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- 网页输入和消息按不可信内容处理，校验消息类型、发送方及参数。展示文本优先 textContent，不把网页文字拼成可执行 HTML。注入和清理不得破坏原网页。
- 执行逻辑随包提供，避免 CDN 脚本、下载代码后执行、字符串 eval。远程 API、图片、普通数据依行为判断，不一概当违规代码。[MV3 要求](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)
- 扩展文件用户可查看，不能放服务端私钥或开发者长期密钥。付费 AI/服务先明确数据接收方及费用承担方式，再做服务和授权，不套用开发者个人凭证。
- 不支持的内部页、未获站点权限、断网、空内容、重复点击分别给实际提示。确定原因后才指导刷新或授权，不把所有错误归因于用户环境。

## 界面与逐票循环

按 product-designer 已定义的 [使用闭环](product-loop.md) 实现可发现的再次操作、结果处理、退出与恢复；基本路径遗漏时先补 AC，不以用户未逐项指定为由省略。围绕主要动作组织入口，结果可见，成功后说明保存在哪里。空态说下一步，错误说明恢复方法；处理中避免重复提交，取消保留约定成果。适配实际 popup/侧栏尺寸，长文可滚动；表单有标签、键盘可达、焦点可见。有确认参考图才对照，有动效才检查减少动效。

不把安装脚本、进度字段、开发说明放进插件日常界面。插件使用者只需自己的操作，开发 skills 和任务记录属于制作者。

循环：读取真实实施票 → 执行 chrome-extensions（复杂项目同时执行 implement）→ 实现完整小功能并正式构建 → 默认 Playwright MCP 加载当前产物并核对 ID/版本 → 原生入口端到端核心操作及适用关闭重开 → 故障执行 diagnosing-bugs 并复验 → 执行 code-review 双轴审查 → 保存版本和调用证据 → 验收门禁通过 → 关闭实施票。Playwright MCP 不支持时必须先取得用户安装/启用或替代选择，不能自行换工具。

按真实风险验证存储、权限、异步消息和迁移，不为微小可逆文案写镜像测试。逐票真实使用检查不推迟到发布前；模拟 API、单独打开弹窗页面及静态检查不能替代。新示例遵循同一循环。必需真实检查尚未通过时，实施票保持进行中或因明确外部依赖而 `blocked`。按 `acceptance.md` 先执行 `acceptance_gate.py fingerprint BUILD_DIR`，将实际证据写成 JSON，再执行 `check BUILD_DIR --evidence JSON --report NEW_PATH`，保存 `gate_passed: true` 的报告及路径。

## 首次试用及排错

由 AI 默认使用 Playwright MCP 完成首次真实端到端试用。按 `dependencies.md` 探测扩展加载和原生入口能力；缺失或不支持时保持 blocked，明确询问安装/启用或推荐受控替代，并等待选择。已获相同环境选择则沿用；不自行换 MCP，不默认交回整份人工验收表，也不使用未被选定的日常 Chrome。

只有受控环境中无法自动化的原生环节确实需本人操作时，才参考 Chrome 当前[本地加载教程](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world)：扩展管理页 → 开发者模式 → “加载已解压的扩展程序” → 确切运行目录 → 工具栏入口。每次只给当前所需一步和确切测试配置/目录，核实实际结果后由 AI 接回端到端验证；依赖该步的交付保持 `blocked`，不让用户替 AI 做完整验收。

更新本地版先核对扩展 ID、加载路径、版本、扩展是否重载、网页内容脚本是否需要刷新。不为测试清空或重启用户主浏览器配置；通过已授权的浏览器通道管理测试环境。

发生“没反应”、报错、构建失败或验收失败时，必须实际读取并执行 diagnosing-bugs。先建立能判定这次具体故障的失败循环、保存最小复现，再提出可证伪原因并逐项验证；在正确的行为边界保留回归检查，修复后复跑原场景及受影响路径。能自行查到的环境事实不问用户，技术排查由 AI 决策；缺少真正影响复现的场景信息时才问。日志与结果按普通语言说明，不以包内这段摘要替代技能阶段，不改预期来制造通过。新增承诺回规格流程。
